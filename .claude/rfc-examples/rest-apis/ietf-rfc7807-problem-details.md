# RFC 7807: Problem Details for HTTP APIs

**Source:** IETF RFC 7807
**URL:** https://www.rfc-editor.org/rfc/rfc7807.txt
**Published:** March 2016
**Category:** Standards Track

## Abstract

This specification defines "problem details" as a way to carry machine-readable details of errors in HTTP response bodies. It avoids the need to define new error response formats for HTTP APIs.

## Motivation

### Problems with Traditional Error Responses

1. **Inconsistent formats**: Every API defines its own error structure
2. **Limited machine-readability**: Hard for clients to parse systematically
3. **Inadequate context**: Status codes alone don't provide enough information
4. **No extensibility**: Difficult to add API-specific error details

### Solution

A standard, extensible format for communicating errors that:
- Works across all HTTP APIs
- Is both human and machine-readable
- Allows API-specific extensions
- Maintains backward compatibility

## Problem Details Object

### Core Members

#### type (string, URI reference)

- **Purpose**: Identifies the problem type
- **Characteristics**:
  - Should be a URI that identifies the problem type
  - When dereferenced, should provide human-readable documentation
  - Consumers should use this for programmatic identification
- **Default**: "about:blank" (no additional semantics beyond status code)

**Example:**
```json
"type": "https://example.com/probs/out-of-credit"
```

#### title (string)

- **Purpose**: Short, human-readable summary of the problem type
- **Characteristics**:
  - Should not change between occurrences (except for localization)
  - Should be the same for all occurrences of the same type
- **Not for**: Specific occurrence details (use "detail" instead)

**Example:**
```json
"title": "You do not have enough credit."
```

#### status (number)

- **Purpose**: HTTP status code generated by the origin server
- **Characteristics**:
  - Primarily advisory
  - Allows problem details to be self-contained
  - Must match the actual HTTP status code if present

**Example:**
```json
"status": 403
```

#### detail (string)

- **Purpose**: Human-readable explanation specific to this occurrence
- **Characteristics**:
  - Focuses on helping client understand this specific problem
  - May change between occurrences
  - Should not include debugging information (stack traces, etc.)

**Example:**
```json
"detail": "Your current balance is 30, but that costs 50."
```

#### instance (string, URI reference)

- **Purpose**: URI reference identifying the specific occurrence
- **Characteristics**:
  - May or may not be dereferenceable
  - Often points to error logs or incident tracking
  - Helps with debugging and support

**Example:**
```json
"instance": "/account/12345/msgs/abc"
```

## Complete Example

```json
{
  "type": "https://example.com/probs/out-of-credit",
  "title": "You do not have enough credit.",
  "status": 403,
  "detail": "Your current balance is 30, but that costs 50.",
  "instance": "/account/12345/msgs/abc",
  "balance": 30,
  "accounts": ["/account/12345", "/account/67890"]
}
```

## Extension Members

APIs can extend the problem details object with additional members:

### Guidelines for Extensions

1. **Use meaningful names**: Choose descriptive property names
2. **Document extensions**: Explain each extension in problem type documentation
3. **Keep focused**: Extensions should relate to the problem, not general data
4. **Consider privacy**: Avoid exposing sensitive information
5. **Be consistent**: Use same extensions for same problem types

### Extension Example

```json
{
  "type": "https://example.com/probs/validation-error",
  "title": "Validation Failed",
  "status": 400,
  "detail": "The request body contains invalid data.",
  "instance": "/requests/12345",
  "validation_errors": [
    {
      "field": "email",
      "message": "Invalid email format"
    },
    {
      "field": "age",
      "message": "Must be at least 18"
    }
  ]
}
```

## Media Types

### application/problem+json

JSON representation of problem details.

**Content-Type header:**
```
Content-Type: application/problem+json
```

**Example:**
```json
{
  "type": "https://example.com/probs/not-found",
  "title": "Resource Not Found",
  "status": 404,
  "detail": "The requested resource does not exist.",
  "instance": "/items/abc123"
}
```

### application/problem+xml

XML representation of problem details.

**Content-Type header:**
```
Content-Type: application/problem+xml
```

**Example:**
```xml
<?xml version="1.0" encoding="UTF-8"?>
<problem xmlns="urn:ietf:rfc:7807">
  <type>https://example.com/probs/not-found</type>
  <title>Resource Not Found</title>
  <status>404</status>
  <detail>The requested resource does not exist.</detail>
  <instance>/items/abc123</instance>
</problem>
```

## Defining Problem Types

### Problem Type URI

Should include:
- **Domain ownership**: Use your domain in the URI
- **Stable paths**: Don't change URIs once published
- **Documentation**: Provide human-readable docs at the URI

**Example structure:**
```
https://api.example.com/errors/{problem-type-identifier}
```

### Problem Type Documentation

Should include:
- **Description**: What this problem type means
- **When it occurs**: Conditions that trigger this error
- **How to resolve**: Suggested client actions
- **Extensions**: Any custom members and their meaning
- **Examples**: Sample problem details objects

## Best Practices

### For API Designers

1. **Create problem type catalog**: Document all problem types
2. **Use consistent URIs**: Follow a pattern for problem type URIs
3. **Be specific**: Create distinct types for different error scenarios
4. **Include context**: Use extensions to provide actionable information
5. **Consider localization**: Support multiple languages for title/detail

### For API Implementers

1. **Always include type**: Even if just "about:blank"
2. **Match status codes**: Ensure "status" matches HTTP status
3. **Avoid debugging info**: Don't leak stack traces or internals
4. **Be consistent**: Use same format for all errors
5. **Validate extensions**: Ensure custom members are properly structured

### For API Consumers

1. **Check type first**: Use type URI for programmatic handling
2. **Ignore unknown extensions**: Be liberal in what you accept
3. **Display detail to users**: Show human-readable messages
4. **Log instance**: Save for debugging and support
5. **Don't rely on title**: It may be localized or change

## Security Considerations

### Information Disclosure

**Risks:**
- Exposing internal implementation details
- Revealing system architecture
- Leaking sensitive data in error messages
- Providing attack vectors through verbose errors

**Mitigations:**
1. **Separate internal and external errors**: Don't expose internal messages
2. **Sanitize details**: Remove sensitive information before sending
3. **Use generic types**: Don't create overly specific problem types
4. **Limit extensions**: Only include necessary information
5. **Log internally**: Keep detailed info in server logs, not responses

### Attack Surface

**Considerations:**
- Problem type URIs as enumeration vectors
- Using instance URIs to probe system resources
- Extensions revealing business logic
- Timing attacks through detailed error messages

**Best Practices:**
1. **Consistent timing**: Don't leak information through response times
2. **Limit enumeration**: Don't create problem types for every condition
3. **Validate URIs**: Ensure problem type URIs are safe to dereference
4. **Rate limit errors**: Apply rate limiting to error responses too

### Privacy

**Guidelines:**
1. **No personal data**: Avoid including PII in problem details
2. **Anonymize instances**: Don't use user IDs in instance URIs
3. **Consider GDPR**: Ensure compliance with privacy regulations
4. **Audit logs**: Separately log detailed info, don't send in response

## Content Negotiation

Clients should indicate preference for problem details:

```http
GET /api/resource HTTP/1.1
Accept: application/json, application/problem+json
```

Servers should respect these preferences:

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{
  "type": "https://example.com/probs/not-found",
  "title": "Not Found",
  "status": 404
}
```

## Migration Strategies

### From Custom Error Formats

1. **Support both formats**: During transition period
2. **Use content negotiation**: Let clients choose format
3. **Document migration**: Provide migration guide
4. **Deprecation timeline**: Set clear end date for old format

### Maintaining Compatibility

1. **Keep existing extensions**: Don't break existing clients
2. **Add, don't change**: Extend problem types, don't modify
3. **Version problem types**: Use URIs to version if needed
4. **Communicate changes**: Announce changes to problem types

---

**Key Takeaways for REST API Error Handling:**

1. Use RFC 7807 problem details format for all error responses
2. Define clear problem types with stable URIs
3. Include both machine-readable (type) and human-readable (title, detail) information
4. Use extensions to provide API-specific context
5. Document all problem types in API documentation
6. Balance informativeness with security (don't leak sensitive details)
7. Be consistent across all API endpoints
8. Support content negotiation for problem details media types
