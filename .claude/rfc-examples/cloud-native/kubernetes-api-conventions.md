# Kubernetes API Conventions

**Source**: https://kubernetes.io/docs/reference/using-api/api-concepts/
**Source**: https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md
**Type**: Foundation-defined API specification
**Domain**: Container orchestration platform

## Overview

The Kubernetes API conventions define a resource-based (RESTful) programmatic interface provided via HTTP that enables retrieval, creation, updating, and deletion of primary resources via standard HTTP verbs.

### Core Design Principles

- **Resource-based architecture**: Everything is treated as an API object
- **RESTful interface**: Uses standard HTTP verbs (POST, PUT, PATCH, DELETE, GET)
- **Efficient change notifications**: Supports "watches" for real-time updates
- **Consistent configuration**: Unified mechanisms across all resources
- **Client development ease**: Predictable patterns and conventions

## Key Terminology

- **Resource Type**: Name used in URL (e.g., `pods`, `namespaces`, `services`)
- **Kind**: Concrete representation/object schema of a resource type
- **Collection**: List of resource type instances
- **Resource/Object**: Single instance of a resource type
- **API Group**: Set of resources exposed together

## Resource Naming and URI Patterns

### Object Names
- Unique names required for objects of same kind
- Within a namespace, only one object of a given kind can have a specific name
- Some objects (like Nodes) have cluster-wide unique name requirements

### Resource URI Patterns

**Cluster-scoped resources**:
```
/apis/GROUP/VERSION/RESOURCE_TYPE
/apis/GROUP/VERSION/RESOURCE_TYPE/NAME
```

**Namespace-scoped resources**:
```
/apis/GROUP/VERSION/namespaces/NAMESPACE/RESOURCE_TYPE
/apis/GROUP/VERSION/namespaces/NAMESPACE/RESOURCE_TYPE/NAME
```

**Core API (legacy)**:
```
/api/v1/RESOURCE_TYPE
/api/v1/namespaces/NAMESPACE/RESOURCE_TYPE
```

### Subresources
- Accessed via specific URI paths appended to resource path
- Example: `/api/v1/namespaces/default/pods/mypod/status`
- Support varies by object type
- Cannot access sub-resources across multiple resources simultaneously

## API Versioning

### Versioning Levels

Kubernetes uses three stability levels for API versions:

**Alpha** (e.g., `v1alpha1`):
- Built-in alpha API versions disabled by default
- Must be explicitly enabled
- May be dropped at any time without notice
- API may change incompatibly in later releases
- Recommended only for short-lived testing clusters

**Beta** (e.g., `v2beta3`):
- Built-in beta API versions disabled by default
- Must be explicitly enabled
- Schema/semantics may change incompatibly
- Not recommended for production
- Subsequent releases may introduce breaking changes

**Stable** (e.g., `v1`, `v2`):
- Version name is `vX` where X is an integer
- Remain available for all future releases within major version
- Subject to strong backward compatibility guarantees

### API Deprecation Policy

- New API resources and fields can be added frequently
- Elimination of resources or fields requires following deprecation policy
- Kubernetes maintains compatibility for GA (v1+) APIs
- Compatibility maintained for data persisted via beta API versions

## Object Structure

### Required Object Components

Every Kubernetes object MUST include:

**1. Metadata** (`metadata` field):
- `namespace`: DNS-compatible label for scope
- `name`: Unique identifier within namespace
- `uid`: Unique time and space value (UUID)

**2. Resource Version** (`metadata.resourceVersion`):
- Identifies internal version of object
- Used for optimistic concurrency control
- Clients must treat as opaque strings

**3. Generation** (`metadata.generation`):
- Sequence number representing desired state
- Incremented when spec changes
- Used to track configuration changes

**4. Timestamps**:
- `creationTimestamp`: RFC 3339 creation date/time
- `deletionTimestamp`: RFC 3339 deletion date/time (when present)

**5. Labels** (`metadata.labels`):
- Organizational key-value pairs
- Used for grouping and selection
- Keys must be DNS subdomain prefixes (optional) + name
- Values up to 63 characters

**6. Annotations** (`metadata.annotations`):
- Non-identifying metadata
- Used by external tooling
- Not used for object selection
- Can contain arbitrary string data

### Spec and Status Pattern

**Spec** (`spec` field):
- Describes desired state
- Complete configuration specification
- Includes user settings and system-generated defaults
- Persisted in stable storage (etcd)
- Idempotent - can be applied multiple times

**Status** (`status` field):
- Describes current observed state
- Generated by automated processes and controllers
- Reflects most recent observations
- Not persisted as source of truth (reconstructible)
- Should summarize present condition

### Conditions

Standard mechanism for status reporting across all resources:

```yaml
conditions:
- type: Ready              # Condition type (CamelCase)
  status: "True"           # True, False, or Unknown
  reason: AllHealthy       # Programmatic identifier (CamelCase)
  message: "All replicas are ready"  # Human-readable explanation
  lastTransitionTime: "2025-01-15T10:30:00Z"
  observedGeneration: 5
```

**Condition Guidelines**:
- Conditions are a list of condition objects
- Each type should be unique in the list
- `Unknown` status indicates unable to determine state
- `reason` provides programmatic cause identifier
- `message` provides human-readable details
- `observedGeneration` links to spec generation

## Types (Kinds)

Kubernetes defines three primary categories:

### 1. Objects
- Persistent entities in the system
- Represent a record of intent
- Have both `spec` and `status` sections
- Examples: `Pod`, `Service`, `Deployment`, `ReplicationController`

### 2. Lists
- Collections of resources of one or more types
- Kind name MUST end with "List"
- Contain an `items` field with array of objects
- Examples: `PodList`, `ServiceList`, `NodeList`
- Two list types:
  - **Resource collections**: Same-version objects
  - **API group discovery**: Mixed versions

### 3. Simple Kinds
- Used for specific operations
- Non-persistent entities
- Don't follow spec/status pattern
- Example: `Status` kind returned during errors

## API Encoding and Content Negotiation

### Supported Media Types

**JSON** (default):
- Content-Type: `application/json`
- Most widely supported
- Human-readable

**YAML**:
- Content-Type: `application/yaml`
- Common for configuration files
- Human-friendly for manual editing

**Protobuf** (binary):
- Content-Type: `application/vnd.kubernetes.protobuf`
- More efficient for large responses
- Uses envelope wrapper with 4-byte magic number prefix
- Includes TypeMeta for kind and apiVersion
- Not all resource types support Protobuf

**CBOR**:
- Content-Type: `application/cbor`
- Binary JSON alternative

### Content Negotiation Rules

- Clients specify preferences via HTTP `Accept` header
- Server returns `406 Not Acceptable` if requested media type unavailable
- Server may transform between equivalent representations
- Default to JSON if no preference specified

## HTTP Verbs and Operations

### Standard Operations

| HTTP Method | Kubernetes Operation | Description |
|-------------|---------------------|-------------|
| GET | get, list, watch | Retrieve resource(s) |
| POST | create | Create new resource |
| PUT | update | Replace entire resource |
| PATCH | patch | Update specific fields |
| DELETE | delete, deletecollection | Remove resource(s) |

### Special Operations

**LIST**: Retrieve all resources of a type
- Supports filtering via field selectors and label selectors
- Returns collection (e.g., `PodList`)
- Paginated for large result sets

**WATCH**: Stream changes to resources
- Long-running GET request
- Returns stream of modification events
- Event types: ADDED, MODIFIED, DELETED
- Used for real-time synchronization

**PATCH**: Partial updates
- Strategic Merge Patch (Kubernetes-specific)
- JSON Merge Patch (RFC 7386)
- JSON Patch (RFC 6902)
- Apply (Server-Side Apply)

## Primitive Types and Conventions

### Type Preferences

- **Prefer `int32` over `int64`**: Unless truly needed
- **Use `int64` for**: Timestamps, large counts, byte quantities
- **Avoid unsigned integers**: Not supported in all languages
- **Boolean**: Use `bool` type, not integer flags

### Field Naming

- Use `camelCase` for field names
- Start with lowercase letter
- No underscores or hyphens
- Abbreviations should be all lowercase (e.g., `http`, `url`)

### Units

Always specify units in field names when applicable:

- **Time durations**: Append unit (e.g., `timeoutSeconds`, `periodMinutes`)
- **Byte quantities**: Use `Quantity` type with SI or binary prefixes
- **Percentages**: Append `Percent` or `Ratio` to field name
- **Timestamps**: Use RFC 3339 format in `metav1.Time` type

Examples:
```yaml
timeoutSeconds: 30
memoryLimitBytes: 1073741824  # 1Gi
cpuRequest: "500m"  # 500 millicores
```

### Quantity Type

Special string format for resource amounts:

**Decimal (SI units)**:
- `100M` = 100,000,000
- `1G` = 1,000,000,000

**Binary (power-of-two)**:
- `100Mi` = 104,857,600 (100 × 1024²)
- `1Gi` = 1,073,741,824 (1024³)

**Fractional**:
- `1.5` = 1500m (milliunits)
- `500m` = 0.5

## Concurrency Control and Consistency

### Resource Versioning

- Every object has `resourceVersion` metadata field
- Opaque string representing internal version
- Changes whenever object is modified
- Used for optimistic locking

### Optimistic Concurrency

**Read-Modify-Write pattern**:
1. GET resource (includes resourceVersion)
2. Modify in memory
3. PUT with original resourceVersion
4. If conflict (409), retry from step 1

**Precondition headers**:
- `If-Match: "12345"` - Only update if resourceVersion matches
- `If-None-Match: "*"` - Only create if doesn't exist

### Consistency Guarantees

- **Strong consistency**: Reads after writes are consistent
- **Atomic operations**: Updates are atomic per-object
- **Ordering**: Watch events maintain causal ordering
- **Durability**: Writes persisted to etcd before acknowledgment

## Field Selection and Filtering

### Label Selectors

Query resources by label key-value pairs:

```
?labelSelector=environment=production,tier=frontend
?labelSelector=environment+in+(production,staging)
?labelSelector=tier,!deprecated
```

**Operators**:
- `=` or `==`: Equality
- `!=`: Inequality
- `in`: Set membership
- `notin`: Set exclusion
- Existence: Key present (no operator)
- Non-existence: `!key`

### Field Selectors

Query resources by field values:

```
?fieldSelector=metadata.name=nginx
?fieldSelector=metadata.namespace=default,status.phase=Running
```

**Limitations**:
- Only specific fields supported (varies by resource)
- Common: `metadata.name`, `metadata.namespace`
- Status fields: Limited support

## Lists and Pagination

### List Metadata

Lists contain metadata for pagination:

```yaml
metadata:
  resourceVersion: "12345"
  continue: "eyJydiI6IjEy..."
  remainingItemCount: 150
```

### Pagination Parameters

**Query parameters**:
- `limit`: Maximum items per page
- `continue`: Token from previous response
- `resourceVersion`: Consistency point

**Example workflow**:
1. GET `/api/v1/pods?limit=50`
2. Response includes `continue` token
3. GET `/api/v1/pods?limit=50&continue=eyJydiI6...`
4. Repeat until `continue` is empty

### Chunking Large Lists

- Server may split large lists automatically
- Clients MUST handle `continue` tokens
- Recommended for lists over 500 items

## API Discovery

### Discovery Documents

Kubernetes provides machine-readable API information:

**API Group Discovery** (`/apis`):
- Lists all API groups
- Versions within each group
- Preferred versions

**API Resources** (`/apis/GROUP/VERSION`):
- Resource types in the version
- Supported verbs per resource
- Subresources available
- Namespaced vs cluster-scoped

**OpenAPI Schema**:
- `/openapi/v2`: OpenAPI 2.0 spec
- `/openapi/v3`: OpenAPI 3.0 spec
- Complete schema definitions for all types

## Idempotency

### PUT Requests
- MUST be idempotent
- Repeated identical PUTs produce same result
- Replace entire resource

### POST Requests
- Generally NOT idempotent (creates new resources)
- Each POST may create new object with unique UID
- Exception: POST for actions (subresources) may be idempotent

### PATCH Requests
- Strategic Merge Patch is idempotent
- JSON Merge Patch is idempotent
- JSON Patch may not be idempotent (depends on operations)

## Optional vs Required Fields

### Required Fields
- Must be present in API requests
- Server rejects requests missing required fields
- Indicated in OpenAPI schema

### Optional Fields
- May be omitted
- Server applies defaults when applicable
- Three categories:
  1. **Defaulted**: Server fills in missing value
  2. **Nullable**: Explicitly set to null has meaning
  3. **Omitempty**: Absence has no special meaning

### Defaulting Behavior

- Defaults applied during API request processing
- Returned value includes defaults
- Clients see fully-defaulted objects
- Defaults may change between API versions (carefully)

## Late Initialization

Some fields populated after creation:

- **System-assigned values**: UIDs, creation timestamps
- **Controller-filled values**: Status fields, observed state
- **Asynchronous defaults**: May appear on subsequent reads

Clients must handle fields absent on create but present later.

## References to Related Objects

### Object References

Standard structure for referencing other objects:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  serviceAccountName: myserviceaccount  # Simple name reference (same namespace)
  nodeName: node-1  # Simple name reference (cluster-scoped)
  volumes:
  - name: config
    configMap:
      name: myconfigmap  # Typed reference structure
```

### Typed References

Full reference structure when needed:

```yaml
targetRef:
  apiVersion: v1
  kind: Pod
  namespace: default
  name: mypod
  uid: a1b2c3d4-e5f6-7890-abcd-ef1234567890
  resourceVersion: "12345"
```

### Cross-Namespace References

- Generally discouraged (breaks namespace isolation)
- When needed, must include explicit namespace field
- Some resources prohibit cross-namespace refs (security)

## Lists of Named Subobjects

Pattern for collections within an object:

**Map style** (preferred):
```yaml
containers:
  - name: nginx
    image: nginx:1.19
  - name: sidecar
    image: busybox:1.32
```

**Principles**:
- Each item has unique `name` field
- Name uniqueness within parent object
- Order may not be preserved
- Enables merging strategies in PATCH operations

## Cloud-Native API Design Patterns

### Declarative Configuration

- Specify **desired state**, not imperative commands
- Controllers reconcile actual state to desired state
- Enables automation and self-healing

### Level-Based vs Edge-Based

**Level-based** (Kubernetes approach):
- Describe complete desired state
- Controllers observe current state
- Reconcile differences continuously
- Resilient to missed events

**Not edge-based**:
- Edge-based: React to events/deltas
- More fragile (events can be lost)

### Controller Pattern

- Watch resources for changes
- Compare actual vs desired state
- Take action to reconcile
- Update status to reflect reality

### Finalizers

Mechanism to prevent deletion until cleanup complete:

```yaml
metadata:
  finalizers:
  - kubernetes.io/pvc-protection
  - example.com/custom-cleanup
```

When object deleted:
1. `deletionTimestamp` set
2. Finalizers block actual deletion
3. Controllers perform cleanup
4. Remove their finalizer
5. Object deleted when finalizers empty

## Extension Mechanisms

### Custom Resource Definitions (CRDs)

- Define new resource types
- Automatically get API endpoints
- Support all standard operations (CRUD, watch, list)
- Integrate with kubectl and client libraries

### Admission Webhooks

- **Validating**: Reject invalid requests
- **Mutating**: Modify requests (add defaults, inject sidecars)
- Called before persistence
- Enable policy enforcement

### API Server Aggregation

- Run custom API servers
- Appear as native Kubernetes APIs
- Full control over storage and behavior

## Security Considerations

### Authentication

- Client certificates
- Bearer tokens
- Authentication proxies
- Service account tokens (for in-cluster)

### Authorization

- Role-Based Access Control (RBAC)
- Attribute-Based Access Control (ABAC)
- Webhook-based authorization
- Fine-grained permissions per resource/verb

### Admission Control

- Policy enforcement before persistence
- Namespace lifecycle
- Resource quotas
- Pod security policies/standards

## Performance Characteristics

### Caching and Informers

- Clients should use informers (watch + local cache)
- Reduces API server load
- Provides low-latency access
- Automatic synchronization

### Efficient List Operations

- Use label selectors to filter server-side
- Pagination for large lists
- Avoid listing all resources repeatedly

### Watch Efficiency

- More efficient than polling
- Maintains single connection per resource type
- Bookmarks for progress tracking
- Automatic reconnection with resync

## Summary of Key Patterns

1. **RESTful resource-based API**
2. **Strong typing with OpenAPI schemas**
3. **Declarative desired-state configuration**
4. **Separation of spec (desired) and status (observed)**
5. **Consistent metadata structure**
6. **Optimistic concurrency with resource versions**
7. **Watch for efficient change notifications**
8. **Label selectors for flexible grouping**
9. **Finalizers for graceful deletion**
10. **Extensibility through CRDs and webhooks**
11. **Level-based reconciliation pattern**
12. **Strong backward compatibility guarantees**

These conventions enable Kubernetes to provide a consistent, extensible, and efficient API surface for managing containerized workloads at scale.
